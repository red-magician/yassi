# 論文組み込み用 素材まとめ（mango-grader 実装）

対象論文：*Peel Color Determines Grade but Not Sugar Content in Irwin Mango:
Rethinking the Design of Brix Guarantees*（IEEE形式・8ページ・英文）

この文書は、実装した `mango-grader`（Cloudflare Pages上のPWA）を上記論文に
組み込むための**事実の一覧**です。文章としての構成は別途行う前提で、
「何が検証済みで、何が未検証か」を明示することを最優先にしています。

> **執筆者への最重要注意**：本文書の §6「書いてはいけないこと」を先に読んでください。
> 検証していない主張を書くと査読で崩れる箇所を列挙しています。

## 1. 論文のどこに入るか（マッピング）

| 論文の該当箇所 | 実装との関係 |
|---|---|
| **IV-G. Grade Classification Succeeds on the Same Information** | 実装の中核。ここで報告した等級分類器を、実際に動作するシステムとして実装した |
| **V-D. Practical Implications**（役割分担の提案） | **本実装は、この提案そのものの実行可能性を示す実装例**。論文が「提案」で終わっている部分を「動くもの」にした |
| **III-B/C. Image Acquisition, Patchwork Feature Extraction** | 前処理（背景分離・形態学処理・鮮紅色画素定義）を実装。ただし49指標のpatchworkは**未実装**（3指標版のみ） |
| **III-C 末尾「Calibration is necessary for each imaging condition」** | この要求を、現場スタッフがアプリ上で実行できる機能として実装 |

**最も強い売り**：論文 V-D は「Imaging performs grade classification, automating
seventy percent of fruits at complete agreement and referring the remainder.
Human inspection retains responsibility for defects.」という役割分担を*提案*して
終わっています。本実装は、その役割分担を **(a) 画像＝自動等級判定、(b) 低確信度＝
人間に差し戻し、(c) 傷・ヤニ＝人間が判断（アプリは検出を試みない）** としてそのまま
コード化し、実際にデプロイして動作させたものです。

## 2. 実装したシステム（System Description 用の事実）

### 2.1 構成
- **形態**：PWA（Progressive Web App）。スマートフォンのホーム画面に追加して
  ネイティブアプリのように使用可能。App Store / Google Play 経由の配布は不要
- **ホスティング**：Cloudflare Pages（静的配信）＋ Pages Functions（サーバレス）＋
  D1（SQLiteベースのマネージドDB）
- **稼働URL**：`https://mango-grader.pages.dev`（2026-08時点でデプロイ済み・動作確認済み）
- **ビルドステップなし**：素のES Modules。フレームワーク・バンドラ不使用

### 2.2 推論はすべて端末内（オンデバイス）
**論文に書く価値がある最大の技術的特徴。**

- 学習済みモデル（scikit-learn の `SimpleImputer → StandardScaler →
  LogisticRegression`）の係数を抽出し、**JavaScriptに完全移植**
- OpenCV（`cv2`）の `cvtColor`(RGB→HSV / RGB→Lab)・`morphologyEx`(膨張収縮)・
  `connectedComponentsWithStats`(連結成分ラベリング) を、公開アルゴリズム定義に
  従って**自前でJS再実装**。外部ライブラリ・WASM（OpenCV.js等）・
  ML推論ランタイム（TensorFlow.js等）への依存ゼロ
- 結果：**画像がネットワークを一切出ない**。サーバ側にGPU・推論基盤が不要。
  オフライン動作可能（Service Workerによるキャッシュ）
- 計算はWeb Workerで実行するためUIスレッドをブロックしない

**実装上の最適化（記述に値する）**：膨張・収縮について、「同一の矩形フラット構造要素
による処理を `iterations` 回反復する」ことは「実効カーネルサイズ
`(k-1)×iterations+1` で1回処理する」ことと数学的に厳密に等価である性質を用い、
分離可能なmin/maxフィルタ1パスで実装（ループ不要）。

### 2.3 ヒューマン・イン・ザ・ループ（論文 V-D の実装）
- **選択的予測**：最大クラス確率（`confidence`）が閾値未満の判定を「要確認」として
  UI上で明示し、人間の確認に回す（既定閾値 0.55、較正前は0.7を推奨と文書化）
- **傷・ヤニは自動検出しない**：論文がAUC 0.67–0.70で断念した通り、アプリは
  傷・ヤニの検出を一切試みず、人間の判断に委ねる設計
- **訂正の収集**：判定結果に対し人間が正しい等級を入力できる。その際
  **「色以外の理由（傷・ヤニ等）で等級が下がっているか」を別フラグで記録**する。
  これは論文 III-A の「color_only サブセットのみで学習」という方法論を、
  継続学習のデータ収集段階に組み込んだもの

### 2.4 プライバシーに配慮した継続学習パイプライン
- 判定のたびに、**画像は送信せず**、特徴量（`vr_whole`, `blob_largest_frac`,
  `blob_n`）・判定等級・確信度のみをD1に記録（ユーザーが送信可否をトグルで制御可）
- 人間の訂正も同様に記録
- `/api/export` が、元のPython実装 `retrain.py` がそのまま読める
  `log.jsonl` / `corrections.jsonl` 形式で書き出す。**特徴量が毎回記録されているため、
  再学習に画像を必要としない**
- 安全策（元設計を踏襲）：訂正の付いていない予測は学習に使わない（機械の判定を
  正解として学習し誤りを強化する悪循環の防止）／旧モデルより有意に悪化したら
  自動採用しない

### 2.5 アプリ内較正モード（論文 III-C の要求への応答）
論文は「Calibration is necessary for each imaging condition, since none of the
photographic sets included a reference target.」と述べています。この較正を、
**現場スタッフがブラウザ上で実行できる機能**として実装しました。

- 正解等級付きサンプル写真を追加 → グリッドサーチ実行 → 現在設定とのスコア比較 →
  適用（端末のlocalStorageに保存、いつでも既定値に戻せる）
- グリッド範囲：`a_thr` 12〜44、`h_thr` 20〜58（いずれも2刻み、340通り）。
  元のPython `calibrate_thresholds()` と同一範囲・同一のJA単純ルール
  （`vr_whole ≥ 70% → A`、`≥ 30% → B`、それ未満 → C）でスコアリング
- スコア指標：macro-F1（labels順 C, B, A、`zero_division=0`）

### 2.6 多言語対応
日本語・英語・中国語（簡体字）。辞書ベースの自前i18nエンジン（66キー×3言語）。
ブラウザ言語から自動選択＋手動切り替え。**外国人技能実習生を含む現場での運用**を
想定した機能として位置づけられます。

### 3.2 本実装で新規に検証した数値（すべて実測・再現手順あり）

**(a) JS移植の忠実性 ― ロジスティック回帰**

| 項目 | 結果 |
|---|---|
| sklearn `predict_proba` との一致 | 複数のテスト特徴量ベクトルで**完全一致** |

**(b) JS移植の忠実性 ― 画像処理パイプライン全体（実写真7枚）**

同一の入力（同一解像度にリサイズ済みの同一RGB配列）をPython版とJS版に与えて比較。

| 指標 | 一致状況 |
|---|---|
| 最終等級判定 | **7/7枚 完全一致** |
| `n_px`（果実コア領域の画素数） | **7/7枚 完全一致**（マスク検出・形態学処理・最大連結成分選択がビット単位で一致） |
| `vr_whole` | 7/7枚で差 **0.06ポイント未満** |
| `blob_largest_frac` / `blob_n` | **2/7枚でずれ**（IMG_0163: 45.6% vs 30.9%、IMG_0168: `blob_n` 2 vs 1、IMG_0169: `blob_n` 2 vs 3） |

**ずれの原因（調査済み・再現確認済み）**：OpenCVの8bit `cvtColor(COLOR_RGB2LAB)` は
速度優先の固定小数点近似（内部LUT）を用いており、公式のsRGB→Lab数式を浮動小数点で
計算して最後に1回丸める実装と比べ、**約10%の画素で a\*/b\* が ±1〜2（256階調中）ずれる**
（ランダムRGBでの実測）。本モデルは `a* > 28` という整数閾値で二値化してから連結成分を
数えるため、±1のずれで閾値をまたぐ画素がたまたま2つの鮮紅色領域をつなぐ「橋」に
なっていたり逆に分断していたりすると、面積の合計（`vr_whole`）はほぼ変わらないのに
**連結成分の数（`blob_n`）や最大成分の割合は敏感に変化**する。

**(c) JS移植の忠実性 ― 較正グリッドサーチ**

同じ7枚・同じ340通りのグリッドで、Python `calibrate_thresholds()` と比較。

| | best `a_thr` | best `h_thr` | macro-F1 |
|---|---|---|---|
| Python版 | 18 | 54 | 0.27777777777777773 |
| JS版 | 18 | 54 | 0.2777777777777778 |

**浮動小数点誤差の範囲で完全一致。**（※ このときのラベルは実装一致確認用の暫定値で、
人間の正解等級ではありません。§6参照）

**(d) 計算時間**

| | 340通りのグリッドサーチ（写真7枚） |
|---|---|
| Python版 | **16分46秒** |
| JS版（ブラウザ想定・Node実測） | **約16秒** |

差の理由：Python版はグリッド点ごとに元の20MP JPEGをデコードし直す実装。
JS版は重い前処理（果実マスク検出・形態学処理・Lab変換）を写真ごとに1回だけ行い、
軽い閾値依存部分（鮮紅色画素の判定・連結成分計算）のみをグリッド点ごとに再計算する
2段構成に分離した（`extractCore()` / `vividFeaturesFromCore()`）。
**アルゴリズムは同一で、計算の再利用のみが差**。

**(e) 分布外入力の観察（※解釈は未確定・§6必読）**

実写真7枚（EXIF日付 2018-08-16、約20MP、無彩色背景・単一果実）の判定結果：

| | 値 |
|---|---|
| `vr_whole` の範囲 | **0.001% 〜 19.18%** |
| 学習データの非ゼロ最小値 | **20%台**（`MODEL_CARD.md` 記載） |
| 判定内訳 | B×6（確信度 95〜100%）、C×1（`blob_n=0` ガード発動）、**A×0** |

→ **7枚すべてが学習データの分布外**（モデルが外挿している領域）。

## 4. 論文の主張を補強する材料

1. **論文 V-D の役割分担が実装可能であることの実証**
   「imaging＝等級分類 / human＝傷ヤニ判断 / 低確信度＝差し戻し」という提案を、
   実際に動くシステムとして構築・デプロイした。提案が机上のものでないことを示す。

2. **必要な計算資源が極めて小さいことの実証**
   本タスクは3特徴量のロジスティック回帰であり、深層学習も推論サーバも不要。
   **スマートフォンのブラウザ内で完結**する。これは「等級分類は画像で十分」という
   論文の主張の実務的な含意（＝導入コストが低い）を具体化する。
   対照的に、糖度保証に必要な非破壊センサはハードウェア投資を伴う。
   **論文の結論（保証はロット単位の実測、画像は等級分類に限定）の経済的合理性を
   補強する材料**になる。

3. **論文 III-C「各撮影条件での較正が必要」への実務的解**
   較正を研究者のPython作業ではなく、現場スタッフがブラウザ上で実行できる機能に
   落とし込んだ。論文が指摘した運用上の制約に対する具体的な緩和策。

4. **傷・ヤニの人間判断が、継続学習のデータ品質確保にも効く**
   訂正時に「色以外の理由による降格か」を記録する設計により、論文 III-A の
   color_only 方針を運用中も維持できる。論文の方法論をシステムに埋め込んだ例。

## 5. 論文の記述を拡張・または食い違う点（要注意・要確認）

### 5.1 「規則の再現」か「規則を上回るか」（重要）
- **論文 IV-G**：公式閾値70%/30%を**そのまま適用**し、人間の表面等級を
  **90.4%** で再現したと記述（＝規則の再現）。
- **実装のモデル**：面積率だけでなく**連結性（`blob_largest_frac`, `blob_n`）を
  特徴量に加えたロジスティック回帰**であり、`mango_grader.py` の記述によれば
  **JA公式ルール（面積率のみ）の macro-F1 0.685 を統計的に有意に上回る
  （Wilcoxon p=0.0035）**。

→ これは論文本文には（少なくとも明示的には）書かれていない主張です。
**「公式規則を再現できる」より一歩踏み込んだ「公式規則より人間の判断に近い」という
主張が可能**かもしれません。人間の等級判定は面積率だけでなく「赤がまとまっているか
散っているか」も見ている、という解釈につながります。
**ただし、この Wilcoxon 検定の元データ・手続きを本セッションでは確認していません。**
論文に入れる前に検定の再現を推奨します。

### 5.2 差し戻し基準が論文と異なる
- **論文 Fig.7**：赤被覆率が**閾値に近い**果実を差し戻す（threshold proximity）
- **実装**：**モデルの確信度**（最大クラス確率）が低い果実を差し戻す（confidence-based）

両者は意図は同じですが**別の基準**です。論文の Fig.7（30%差し戻しで完全一致）を
実装の説明に流用しないでください。実装側の対応する数値は `MODEL_CARD.md` の
選択的予測表（60%自動化で100%）で、これも別モデル・別基準の値です。

### 5.3 patchwork特徴量（49指標）は未実装
論文 III-C の49指標は実装していません（3指標のみ）。論文が「49指標にしても糖度は
予測できない」と結論しているため等級分類には不要という判断ですが、
**実装が論文の全手法を含むわけではない**ことを明記してください。

### 5.4 デプロイ時に発見・修正した不具合（論文に書ける知見）
`MODEL_CARD.md` に記録されている、v1公開前に発見された不具合：

> 鮮紅色画素が皆無（緑一色など）の果実を、ロジスティック回帰が**誤ってB判定**する。
> 学習データに「鮮紅色0%」の個体が一度も無かったため、その領域で外挿が暴れたのが原因。

対処：`blob_n == 0` の場合は機械学習モデルを介さず**ルールベースで直接C**と判定する
ガードを追加（JA基準でも鮮紅色0%はC以外にありえないため安全）。

→ **論文 V-E「Methodological Lessons」に第4の教訓として追加できる素材**：
「学習データの範囲外の入力に対する回帰モデルの外挿は、農業現場で現実に発生する
（緑一色の果実は普通に存在する）。ドメイン知識に基づくルールベースのガードを
併用すべき」。実装しなければ気づかなかった種類の知見です。

### 5.5 実装忠実性という新しい再現性の軸
論文 III-D は「同じ果実を2回撮影して指標の再現性を測る」（撮影行為の再現性）を
扱っています。本実装で行った検証は**別の軸**です：
**同一の入力に対して、参照実装（Python/OpenCV）と再実装（JS）が同じ値を出すか**。

結果として、**等級判定は完全一致するが、連結成分ベースの特徴量は
ライブラリの内部近似の違いで一致しない場合がある**ことが判明しました。
これは「画像処理を用いた農業研究の結果を、別環境・別言語で再現・実装する際の
落とし穴」として一般化できる知見で、論文 V-E に追加する候補です。

## 6. 書いてはいけないこと（査読で崩れる箇所）

### 6.1 ⚠ 最重要：7枚の写真を「較正のズレの証拠」として書かないこと
**当初この観察を「較正が合っていない証拠」と解釈しましたが、それは誤りです。**
以下2点の交絡があり、現時点では**原因を特定できていません**。

1. **この7枚には人間による正解等級が付いていない。** 低い判定が誤りなのか正しいのか
   を判定する基準が存在しない。
2. **写真セットの出所が交絡している。** ファイルは `mango_spoil.zip`（フォルダ名も
   `mango_spoil`）として提供され、実際に炭疽病様の黒斑・傷が写っている。
   **傷んだ果実の見本として意図的に選ばれたセットである可能性が高く**、その場合
   着色が低く出るのは「モデルが正しい」という解釈と完全に整合する。

**書いてよい範囲**：「7枚すべてで `vr_whole` が学習データの非ゼロ最小値を下回り、
モデルが分布外領域で外挿していた」という**事実の記述まで**。
**書いてはいけない**：「較正がズレている」「A級が出なくなる失敗が再現された」。

**切り分けに必要なもの**：この撮影環境で撮った、**人間の正解等級付きサンプル**
（A級を含む各等級20枚程度）。A級が正解の果実で実際にA判定が出ないことを確認して
初めて較正のズレと言えます。**論文に載せるなら、この追加データ取得を推奨します。**

### 6.2 較正グリッドサーチのスコア（0.278）を性能値として書かないこと
§3.2(c) の macro-F1 0.278 は、**Python版とJS版の実装一致を確認するためだけに
暫定ラベル（B×6, C×1）を与えて計算した値**です。人間の正解等級ではないため、
**較正の性能・精度を表す数値ではありません**。実装一致の証拠としてのみ使えます。

### 6.3 ブラウザ実機での多言語表示は未確認
i18nの実装はNode上でDOM/localStorageをスタブして検証済みですが、
実機ブラウザでの3言語表示確認は未実施です（デプロイ済みなのは日本語版のみの時点）。

### 6.4 実運用データはまだ存在しない
D1に蓄積される判定ログ・訂正データの仕組みは実装・デプロイ済みですが、
**実際の現場運用による収集データはまだありません**。
「現場で運用した結果」は書けません。

### 6.5 スマホカメラでの実撮影→判定の系統的評価は未実施
デプロイしたアプリが動作することは確認済みですが、
**スマホカメラで撮影した画像に対する判定精度の系統的な評価は行っていません**。
検証に使った7枚はデジタルカメラ撮影（約20MP）の既存写真です。

## 7. 限界（Limitations に追記できる項目）

1. 連結成分ベースの特徴量（`blob_largest_frac`, `blob_n`）は、画像処理ライブラリの
   内部実装差（Lab変換の固定小数点近似）により、実装環境が変わると値が変動しうる。
   等級判定への影響は検証した7枚では見られなかったが、境界付近の個体では
   結果を変える可能性がある。
2. アプリ内較正は色のしきい値（`a_thr`/`h_thr`）の再選択のみで、
   ロジスティック回帰自体の再学習ではない（再学習はオフラインの `retrain.py`）。
3. 学習データの等級不均衡（A=100, B=11, C=3）は未解消。特にC級の性能は
   サンプル数が少なく、見かけ上の高さである可能性が残る。
4. 傷・ヤニの自動検出は実装していない（論文の AUC 0.67–0.70 の結果に基づく判断）。
   最終等級の判定には人間が必須。
5. スマホカメラの撮影条件（ホワイトバランス自動補正、多様な照明、背景の写り込み）は
   2019年の撮影条件と大きく異なるため、実運用前の再較正が必須。
6. `/api/log`・`/api/correction` はオフライン時に静かに失敗する（再送キュー未実装）。
